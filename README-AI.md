# Vibe Coding Context Sheet

**⚠️ Mechanically split** from single-file `InterviewQuestionViewer_v24.html` (verified: valid ES modules, every function/import accounted for) but **not exercised in a browser**. Test features before relying on them; keep the original `.html` as fallback.

## Working agreement
- **Default: never auto-commit/push.** After making the requested code changes, stop and explicitly ask the user whether to commit and push now — wait for their approve/deny before running `git commit`/`git push`.
- **Exception: if the user's message explicitly says "auto commit and push" (or equivalent explicit auto-authorization wording), commit and push without waiting for approval.** That phrase itself is the authorization — don't ask again in that case.

## Architecture
- **Single shared state, no framework.** `js/state.js` exports one mutable `state` (rawData, grouped, activeFilters, flatGroupView, currentFileName, etc.) + localStorage-key constants. Modules mutate `state.x` directly — no reducer/store/event bus.
- **No reactivity.** After mutating state: persist (if applicable) → call `render()` (`js/components/tree.js`) to rebuild `#rootAccordion` from scratch. Nothing auto-renders.
- **Data shape:** `rawData` = flat rows `{Subject, Topic, SubTopic, Question, Answer, Done, ReviewLater, Duplicate, LessImportant, Starred, Order, _id, ...}`. `grouped` = `rawData` regrouped via `groupData()` (`js/utils.js`) into Subject→Topic→SubTopic→[questions]. Rebuild `grouped` after any structural change.
- **Grouping hierarchy: Subject > Topic > SubTopic > Question** (`SubTopic` was renamed from `Level` tool-wide — CSV column, `state.grouped`/`activeFilters` keys, `groupData`/`getExistingOrder`, `js/api.js` CSV/`REQUIRED_COLUMNS`, most of `js/components/tree.js` and `metadata.js`, `index.html#subTopicFilter` all mirror this name). Exception: `.subtopic-alert-holder` class stays lowercase/kebab. Adding a 4th layer means threading it through all these.
- **Filtering separate from grouping.** `filterGroupedData()` (`js/components/filters.js`) prunes `grouped` using `state.activeFilters`; `render()` calls it fresh each time (no cached filtered copy).
- **Persistence:** `js/api.js` owns all localStorage I/O + CSV import/export (PapaParse). Call `persistCurrentProgress()` after any question-data edit.
- **DOM hand-built, not templated.** `createSubject/Topic/SubTopic/Question` (`js/components/tree.js`) each return a node via `createElement`+`appendChild`. Follow this pattern for new tree UI.
- **Cross-cutting UI helpers** in `js/components/fuzzyHints.js`: `flashHighlightItem()` (10s yellow highlight+dismiss icon) and `jumpToQuestion()` (expand+scroll+flash) — reuse for any "take user to a question" affordance.
- **Adding a feature:** state → `state.js`; logic → relevant `components/*.js`; call `render()` (+`persistCurrentProgress()`/`refreshFilterOptions()` as needed); wire new static controls in `js/app.js`.

## Gotchas (read before touching related code)

1. **`.accordion-button` flex-fills its header row** — anything appended after it as a sibling (`controlsEnd`) lands pinned far-right, not next to question text. To place an icon right after `qText`, append it *inside* `button` as a `<span>` (real `<button>` nesting is invalid HTML) wrapped in `status-icon-row compact`, with its own `click` + `e.stopPropagation()`.

2. **Bootstrap 5 data-api toggle listeners run in CAPTURE phase on `document`** — a bubble-phase `stopPropagation()` on any descendant, even the trigger itself, cannot block them (capture fires first). Fix for restricting collapse-toggle to one inner element (e.g. `.q-text-link` only): don't set `data-bs-toggle`/`data-bs-target` on it at all; instead call `bootstrap.Collapse.getOrCreateInstance(collapseEl).toggle()` from a plain click listener on just that element (see `qText` in `createQuestion()`). `data-bs-parent` still works since that's read off the collapse element. Since Bootstrap no longer manages the trigger, manually set `button`'s `.collapsed` class/`aria-expanded` from pre-toggle `collapse.classList.contains("show")`. Reuse this pattern; `stopPropagation`-gating is a dead end against data-api.

3. **`state.activeQuestion` is a single global pointer** (content-keyed `{Subject,Topic,SubTopic,Question}`, never `_id` — `_id` regenerates every load via `uid("q")`, same reason `emptyGroups`/`questionExistsIn()` key off content). `setActiveQuestion`/`clearActiveQuestion`/`isActiveQuestion` (`js/components/tree.js`) deliberately **skip `render()`** (must be inert) — they patch DOM directly (clear any `.icon-flag.is-active` elsewhere, toggle this `flagBtn`) and call cheap `updateHeaderBreadcrumb()`. Persisted via `saveActiveQuestion()`/`readActiveQuestion()` (`js/api.js`). Set only by clicking empty header space; cleared only via its own flag icon.
   - `updateHeaderBreadcrumb()` appends a second element after the chain text: a green flag-icon link to the Active Question (`appendActiveQuestionBreadcrumbLink()`), clicking → `expandToQuestion(qid)` + `flashHighlightItem()`. Built via `appendChild`, not `textContent =`, so future edits must not reintroduce a blanket `textContent` overwrite.

4. **A tree function's `questions` param isn't reliably the full list** — under an active Status filter it's the filtered (shorter) array. Don't compute new `Order` from `questions.length`; use `nextQuestionOrder(subject, topic, subTopic)` (`js/utils.js`, reads `state.rawData` directly).

5. **Sort order:** extend `groupData()`'s tier/comparator (`js/utils.js`) rather than writing a new sort — it already re-sorts every rebuild. A status toggle that affects order should do: `state.grouped = groupData(state.rawData, state.emptyGroups); state.pendingFocusQid = q._id; render(); highlightMovedQuestion(q._id);`.

6. **Empty groups** tracked separately in `state.emptyGroups` (`[{Subject,Topic,SubTopic}]`, null fields = shallower marker). `groupData()` merges them with `order: 1e9 + index` (sorts after real siblings, preserves creation order). Self-prunes each call. `markGroupEmpty()` is the only way to add one — call before `groupData()` rebuild whenever a SubTopic could become empty (delete, cross-SubTopic drag, move panel). `filterGroupedData()` always passes structurally-empty groups through Status filter (still subject to Subject/Topic dropdowns). Renaming (`metadata.js`) must rewrite matching `emptyGroups` entries too. Persisted via `saveEmptyGroups`/`readEmptyGroups`; round-tripped through Progress CSV as marker rows.

7. **Cross-list SortableJS drag:** use `group:` + `onUpdate` (same-list reorder) split from `onAdd` (cross-list drop, fires once on destination) — never `onEnd` (fires for both, ambiguous). See question Sortable in `createSubTopic()`, grouped per-Topic via `"questions-" + parentId`.
   - **Dropping onto a collapsed header** isn't reachable via Sortable's list-linking (no laid-out hidden-list area). Pattern: track `draggingQids`/`draggingSourceKey` module state, hit-test pointer via `document.elementFromPoint` in both a `document` `mousemove`/`dragover` listener (`startHeaderDropTracking()`) AND Sortable's `onMove` (belt-and-suspenders), commit via `finishDragIfHoveringHeader()`. Reuse for any "drop onto a possibly-collapsed summary row" feature.

8. **Full-header overlay/highlight** must be a separate absolutely-positioned (`inset:0`) sibling `<div>` appended into the header, not a class/border on the header itself — in-flow children paint over header-level box decorations. See `.flash-overlay`/`.drop-target-highlight`. `.accordion-header` has `position:relative` globally to anchor it.

9. **Status flags** (Done/ReviewLater/Duplicate/LessImportant/Starred) — adding one touches 4 places: (1) `#statusFilter` option in `index.html`, (2) case in `matchesStatusFilter()` (`filters.js`), (3) toggle wiring in `createQuestion()`/`createAddQuestionPanel()` (`tree.js`), (4) CSV read/write in `api.js` (row parsing, row building, export headers, draft objects).
   - Status icon CSS: `css/style.css` ~L199-320, one block per `.icon-<key>` (default/hover/`.is-active`). Reuse established colors: `orangered`=less, `red`=duplicate, `var(--accent)`=search, `#6f42c1`=move.

10. **`createQuestion()` declares `const`s up top, wires listeners further down** once closed-over vars (`collapse`, `editWrapper`) exist — fine since listener bodies run later. Follow for new header-icon-button-with-later-panel additions.

11. **A header button opening a panel inside the (collapsed) answer body must expand it first:** `if (button.classList.contains("collapsed")) expandItem(button, collapse);` before toggling the panel (see `editQuestionBtn`). Exception: `moveIconBtn`'s shared move form no longer lives inside the collapsed body.

12. **Any action that relocates a question** should end with `state.pendingFocusQid = q._id; render(); highlightMovedQuestion(q._id);` — `render()` alone repositions but doesn't flash.

13. **Bulk selection is a per-parent closure `Set`, not `state`** (transient, cleared implicitly by re-render). Questions-within-SubTopic is hand-written (`selectedQids` in `createSubTopic()`, `selectionCtx` param) since it also drives drag-move. Subject/Topic/SubTopic self-selection uses shared `createGroupSelectionUI(itemNoun, getCheckboxes, isEmpty, bulkDelete)` — one instance per parent, passed down as `{selectedNames, onChange}`. Checkboxes always render, CSS-gated by a `.selecting` class on the specific ancestor (`#subjectAccordion.selecting .subject-select-checkbox` etc., one unique class per level to prevent cross-leak). `selectToggleBtn` doesn't self-wire its click — each caller must wire `toggleSelectingOn(theirElement)` exactly once (double-wiring double-toggles).

14. **`render()` always collapses every open accordion** (`root.textContent = ""` rebuild). `captureOpenState()`/`restoreOpenState()` (`tree.js`, exported) must bracket every mutating action (all delete/bulkDelete, quickAdd/bulkAdd, move, question-add paths) — capture walks pre-render DOM for every open chain (multiple SubTopics can be open per Topic), restore replays via `expandGroupChain()` in a `requestAnimationFrame`, tolerating partially-gone chains. Easy to forget on a new flow — app still "works", just jarringly. Still pair with action-specific focus (`pendingFocusQid`/`highlightNewGroup()`) — restore isn't a substitute for that.

15. **Deleting a Subject/Topic/SubTopic is blocked if any question exists beneath it** — `.tree-delete-btn` computes `flattenQuestions().length`, `alert()`s+returns if nonzero; only a `confirm()` for a provably-empty node reaches `deleteSubjectGroup`/`deleteTopicGroup`/`deleteSubTopicGroup`, which cascade-remove matching `rawData`+`emptyGroups` entries (in practice only empty-marker scaffolding, since populated branches can't reach this path).

16. **The move ("Change Subject/Topic/SubTopic") form is ONE shared instance per SubTopic**, not per question. `createMoveForm(subject, topic, subTopic)` builds it once; operates on closure array `moveTargetQids` (set via `moveForm.openFor(qids)`) so both single-question (`moveIconBtn`) and bulk-selection ("Move Selected") share it. `performMove()` calls the same `moveQuestionsToSubTopic()` used by drag-and-drop — don't reimplement. Has persistent icon-only "+ Add New..." per picker column, plus auto-prompt cascading (Subject/Topic with zero children auto-creates next level) via `maybeAutoPromptTopic`/`maybeAutoPromptSubTopic` → `createTopicAndSelect`/`createSubTopicAndMove` (extend these, not button handlers).

17. **Bulk-adding at any level goes through ONE function: `bulkAddHierarchy(fixedSubject, fixedTopic, rawText)`** (no more per-level `bulkAddSubjects/Topics/SubTopics`). `createBulkAddGroupButton()` is a thin UI shell; call sites pin `fixedSubject`/`fixedTopic` (`null,null` at root; `subject,null` in `createSubject()`; `subject,topic` in `createTopic()`). Each line = tab-separated `[Subject?, Topic?, SubTopic?, Question?, Answer?]`, variable depth — stopping short of Question registers an empty group (`markGroupEmpty()`); reaching Question creates a row (`nextQuestionOrder()`, `uid("q")`, dedup via `questionExistsIn()`). Reads `state.rawData`/`emptyGroups` directly per-line (not cached `grouped`) so a multi-line paste into the same new group stays consistent; `groupData()` rebuilds once at the end. Returns `{groupsAdded, questionsAdded}` (0/0 keeps the draft open). No singular `quickAddSubject()` — bulk-add textarea is the only way to add a Subject (Topic/SubTopic keep both singular `quickAddTopic/SubTopic()` and bulk-add).

18. **Tree copy buttons come in five flavors** (`tree.js`, per Subject/Topic/SubTopic header): `createCopyQuestionsButton()` (Question text, `buildTreeCopyText()`), `createHierarchyCopyButton()` (names only, tab-indented, `buildHierarchyOnlyCopyText()` — SubTopic case is just its own name since it has no sub-hierarchy), `createPlainCopyButton()` (flattened Question-per-line), `createStructureWithAnswerCopyButton()`/`createStructureCopyButton()` (tab-separated row per descendant path, `buildStructureWithAnswerCopyText()`/`buildStructureOnlyCopyText()`). **All five are scoped to own node + descendants only, never ancestors** (`label` = just this node's name — a past bug leaked the parent chain via a `pathParts` ancestor array). The one place a full Subject-down path legitimately appears is the global `copyVisibleQuestionsStructureWithAnswer()`/`copyVisibleQuestionsStructure()` (`js/components/stats.js`), since Subject has no ancestor.

19. **The "flatten" toggle (`state.flatGroupView`, button inside `updateGlobalStatsBadges()`, `js/components/stats.js`) swaps the nested Subject > Topic > SubTopic accordion tree for `renderFlatGroupedView(root, filtered)`** (`js/components/tree.js`, called from `render()` right after the "no data" check, before the nested-tree branch) — one plain, never-collapsing `<p class="flat-group-path">` heading ("Subject/Topic/SubTopic") per group that actually has questions, followed by that group's question accordions. It reuses `createQuestion()` completely unchanged (same status icons/edit/delete/move all work identically) and gives each group its own `createMoveForm()` instance — same "one shared instance per SubTopic" pattern `createSubTopic()` uses — purely so `moveIconBtn` has somewhere to open into; there's deliberately no bulk-select/drag-reorder UI here, since those exist to move things *between* SubTopics, which this flattened view doesn't otherwise represent. Persisted globally (not per-file) via `LS_FLAT_GROUP_VIEW`, read once in `initApp()` (`js/api.js`) — same shape as `editModeOn`/`tempMode`, just without `initPersistedToggle()` since the toggle button itself is rebuilt fresh every `render()` rather than living as a static `index.html` checkbox. `stats.js` importing `render` from `tree.js` (which itself imports `updateGlobalStatsBadges` from `stats.js`) is a circular import — already an established, working pattern in this codebase (`filters.js`/`tree.js` do the same) since both bindings are hoisted function declarations only *called* later, never read at module-evaluation time.

20. **Edit Answer and all four drag handles are ALWAYS visible/usable, independent of Edit Mode — do not re-gate them on `state.editModeOn`.** This used to not be true (both were Edit-Mode-gated); it was deliberately changed. `createQuestion()` (`tree.js`) builds Edit Answer (`editBtn`, text "Edit Answer"/"Add Answer" depending on `q.Answer`) inside its own `answerEditRow` (`class="answer-edit-row"`, styled in `style.css`, appended right after `answerContent`) — a sibling of, and deliberately separate from, `actionsRow` (`class="status-controls"`, still Edit-Mode-gated, holds `editQuestionBtn`/`moveUpBtn`/`moveDownBtn`/`moveTopBtn`/`moveBottomBtn`). `.answer-edit-row` is never listed in any `body.edit-mode-off` CSS rule — that's what keeps it visible. Drag-to-reorder (`Sortable.create(..., { handle: ".drag-handle", ... })`, all four levels — Subject/Topic/SubTopic/Question, grep `Sortable.create` in `tree.js`) is likewise no longer in the `body.edit-mode-off` selector list; `.drag-handle` was removed from it. Edit Answer now has no visibility gate at all (unconditionally visible). **Drag handles instead moved to their own independent toggle** (see point 20a) — when adding new drag affordances, gate them the same way (own class, own toggle), not by piggybacking on `state.editModeOn`.

20a. **Drag & Drop has its own toggle, separate from Edit Mode: `state.dragDropOn` / `LS_DRAG_DROP_ON` (`state.js`), default `true`.** Button (`#`-less, just a `.btn` in the DOM — find it via its icon `fa-arrows-up-down-left-right`) lives in `updateGlobalStatsBadges()`'s `actionsGroup` (`js/components/stats.js`), immediately before the copy-export buttons, same rebuilt-fresh-every-render pattern as the neighboring flatten-view toggle (`flatViewToggleBtn`) — click handler flips `state.dragDropOn`, persists to `localStorage`, toggles `body.drag-drop-off`, then `render()`. `body.drag-drop-off .drag-handle { display:none }` (`style.css`) is the actual enforcement — same "hide the handle so Sortable's `handle:` option has nothing to grab" mechanism `body.edit-mode-off` used to use. Initial state is read once in `initApp()` (`js/api.js`), same shape as `state.flatGroupView`/`LS_FLAT_GROUP_VIEW`, plus (unlike `flatGroupView`) it also sets the `body.drag-drop-off` class at startup since CSS, not just `render()`, depends on it. The toggle button itself still lives inside `#globalStatsBadges`, so it's still hidden while Edit Mode is off (`body.edit-mode-off #globalStatsBadges button`, `style.css` ~L981) — only the drag handles/Edit Answer button were pulled out of Edit-Mode gating, not this control button.

21. **The legacy "Starred Only" view (`#starredOnlyToggle`, `#starredAccordion`, `state.showStarredOnly`, `js/components/starred.js`) was removed entirely** — the `Starred` status flag itself (star icon toggle, Status filter option, CSV column, sort-to-top priority in `groupData()`) is untouched and still fully functional; only the separate "show just my starred questions in one flat list, no hierarchy" view is gone. If something similar is wanted again, `renderFlatGroupedView()` (point 19) is the closer starting point — it already groups-and-flattens the *current* filtered set, so filtering to `Status: Starred` plus flatten-view together now covers most of what the old feature did.

22. **`data.js` (sibling of `index.html`, `var csvString = \`...\`;`) is the seed data `#loadCsvStringBtn` ("Load Sample") loads if present** (`app.js` checks `typeof csvString !== "undefined"`, falls back to `getDefaultSampleCSV()` otherwise) — updating it is a manual copy-paste workflow, not something the app writes to automatically (no filesystem access from the browser). `#copyProgressCsvBtn` (icon-only, next to `#downloadProgressBtn` in `index.html`'s `.toolbar-card`) copies the same CSV text `downloadProgress()` would save to a file, to the clipboard instead, via `navigator.clipboard.writeText()` — for pasting straight into `data.js`'s `csvString` to refresh the seed with latest progress. Both buttons share row-building logic factored into `buildProgressCsv()` (`js/api.js`, returns `""` if nothing to export — callers must check); `downloadProgress()` itself only adds the date/version filename logic on top before calling `triggerDownload()`. `#copyProgressCsvBtn` is enabled/disabled everywhere `#downloadProgressBtn` is (`activateFile()`/`resetAllData()` in `api.js`) — extend both together if a third button needs the same gate. The click handler and `showSuccessAlert()` import live in `app.js`, not `api.js`, specifically to avoid adding a new `api.js` → `fuzzyHints.js` import edge (`fuzzyHints.js` already imports `persistCurrentProgress` from `api.js` — an `api.js` → `fuzzyHints.js` import back would be circular; `app.js` importing `fuzzyHints.js` is not, since nothing imports `app.js`).
